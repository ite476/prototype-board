# 제품 기준 비교본

기존 UI를 기준으로 개선 시안을 만들거나 Before/After 대조본을 요청받았을 때 적용한다. 새 제품 디자인을 요청한 경우까지 기존 화면 보존을 강제하지 않는다.

## 기존 화면의 근거

- 제품·저장소·화면 경로와 실제 읽은 커밋을 기록한다. FE와 BE가 다른 저장소이면 각각 확인한다. `origin/main`이라는 이름만으로 최신 코드나 운영 화면이라고 단정하지 않는다.
- 실행 화면, 제공받은 이미지, 소스코드 중 무엇을 확인했는지 적는다. 소스에서 재구성한 화면은 “코드 기준 재구성”, 일부만 확인했다면 “부분 재구성”으로 표시한다. 자료가 없으면 Before를 상상해서 채우지 말고 필요한 화면이나 저장소를 요청한다.
- 메뉴·탭·표의 열·필터·버튼 위치·정보 밀도·디자인 토큰·공통 컴포넌트를 확인한다. 이미 제공되는 오류 문구·툴팁·선택 제한도 Before에 반영한다. 개선 효과를 크게 보이려고 기존 안내를 없애지 않는다.
- 확인한 사실, 제안, 미정 사항을 구분한다. HTML로 외관을 재현했다면 실제 제품 컴포넌트나 API를 실행했다고 말하지 않는다.

## 비교 화면 제작

같은 제품 화면의 Before/After는 같은 화면 크기·초기 샘플 데이터·선택 조건으로 시작한다. 기존 화면의 배치와 기능을 출발점으로 삼되, 기획상 필요한 재배치와 새 흐름은 바꾼 이유를 적고 표현한다. 누락 경고 때문에 요청과 관계없는 화면 전체 재설계를 추가하는 식으로 범위를 넓히지 않는다. 서로 다른 관점까지 같은 크기를 강제하지 않는다. 예를 들어 관리자 웹은 데스크톱 폭, 사용자 앱은 모바일 폭, 시스템 흐름은 도식에 맞는 크기로 비교할 수 있다.

- 나란히 비교와 Before/After 각각 크게 보기를 기본으로 고려한다. 단계별 흐름이나 긴 도식은 탭·위아래 배치·단계 전환 등 기획에 맞는 비교 방식을 쓸 수 있다. 어떤 방식을 쓰든 같은 단계의 변경 전후를 찾고 읽을 수 있어야 한다. 폭이 좁을 때 표를 작은 글씨로만 압축하지 말고 원래 크기로 읽을 방법을 둔다.
- 비교 모드·변경 강조 전환은 시연 중 선택이나 입력을 초기화하지 않는다. 초기화와 예시 상태 전환은 명시적인 별도 조작으로 둔다. 양쪽 상태가 서로를 변경하지 않게 한다.
- 변경 강조·시나리오 선택·개발 범위 설명은 제품 화면 바깥의 검토 영역에 둔다. 실제 제품의 버튼처럼 보이게 만들지 않는다.
- 기본 상태, 빈 상태, 조회 실패 및 제안한 기능의 성공·실패를 필요한 만큼 재현한다. 보완·저장 시도와 실제 성공을 구분하고, 실패했는데 완료로 보이는 시연을 만들지 않는다.
- 권한·부분 성공·차단 조건이 미정이면 시안의 제한을 정책 확정으로 설명하지 않는다. 기존 업무 규칙을 바꾸는 제안은 시각적 변경과 별도로 기록한다.
- 생략한 메뉴·축약한 하위 행·동작하지 않는 기존 기능을 표시한다. 검토용 틀의 예시 화면과 근거 설명은 실제 확인 내용으로 교체한다.
- 같은 사례를 비교한다는 뜻이 Before에 없는 기능까지 구현하라는 뜻은 아니다. 기존 제품이 처리하지 못하는 입력이라면 확인한 제한을 보여준다. 기존 동작의 근거를 확인하지 못했으면 그 부분을 미확인으로 남긴다. 원본 데이터와 비교 시작 조건은 맞추되, 새로 제안한 처리 결과까지 양쪽에 강제로 맞추지 않는다.

### 틀을 기획에 맞게 바꾸기

`../assets/product-comparison.html`은 선택해서 쓰는 시작 예시이며 필수 화면 규격이 아니다. 특정 제품의 스타일이나 업무 규칙을 제공하지 않는다. 필요한 부분만 복사하거나 독립 HTML을 새로 작성해도 된다.

- `.sample-product`와 `renderProduct`뿐 아니라 화면 폭·레이아웃·비교 도구·시나리오·상태 모델·화면 전환도 바꿀 수 있다. 예시의 1120px 폭, 표 두 개, 메모·체크박스를 유지할 필요는 없다.
- 데이터 흐름은 단계와 연결선, 관리자 화면은 표·상세 창, 사용자 앱은 모바일 화면과 하단 탐색처럼 목적에 맞게 구성한다. 화면별 비교가 더 명확하면 각 관점에 서로 다른 틀을 써도 된다.
- 검토에 필요 없는 강조·원래 크기·시나리오 버튼은 제거하거나 다른 읽기·비교 방법으로 대체한다. 남겨 둔 표시 전환은 입력을 보존하고, 입력을 초기화하는 조작은 그 효과를 분명하게 알린다.
- 틀을 바꾼 뒤에는 기존 예시의 검증 결과를 그대로 이어 쓰지 않는다. 실제 결과물에서 변경 전후의 근거, 같은 사례의 대응, 상태·수량 조건, 독립 실행과 주요 동작을 다시 확인한다. 파일 형식과 외부 의존성 제한은 그대로 적용한다.

기능의 상태 전환은 확인한 기존 규칙과 명시한 신규 제안으로 작성한다. 보드 서버·저장 형식은 바꿀 필요가 없다.

## 여러 화면과 데이터 흐름 비교

하나의 기능이 여러 제품·역할·화면에 걸치면 [공통 기획과 표현별 결과물](core-and-adapters.md)을 함께 적용한다. 단일 안내 문구 개선에 아래 항목을 모두 요구하지는 않는다.

- **검토 관점과 기능 선택지를 나눈다.** 시스템·관리자·사용자 앱은 같은 기능을 확인하는 관점이다. 저장 방식 A/B처럼 서로 다른 설계 선택지는 각 관점의 After 안에서 비교하거나 별도 변형으로 명시한다. 관리자 화면과 사용자 앱을 서로 경쟁하는 채택안으로 취급하지 않는다.
- **화면 목록을 먼저 만든다.** 화면 경로·기존 조회 값·추가 값·사용자 행동·영향 종류·비교본 위치를 연결한다. 직접 화면이 바뀌는 곳, API나 집계만 영향을 받는 곳, 아직 확인하지 못한 곳, 변경 근거가 없는 곳을 구분한다. 대표 화면 하나를 만들고 전체 화면 검토를 마쳤다고 보고하지 않는다.
- **데이터가 실제로 이동하는 경로를 보여준다.** 원본 입력 → 검증 → 분할·배정 → 저장 → 실행·실패 → 결과 집계 순서에서 이번 기능과 관련된 구간을 비교한다. 각 단계에 처리 주체, 원본·작업 식별자, 읽고 쓰는 값, 성공·실패 후 남는 상태를 적는다. 확인한 API·필드와 새 구조 제안을 구분한다.
- **분할 단위와 집계 단위를 적는다.** 원본 항목을 복제하는 것과 원본을 유지하면서 작업별 수량을 따로 기록하는 것은 다르다. 화면에 같은 원본이 여러 번 나타나면 원본 수량·배정량·완료량 중 무엇을 합산하는지 확인한다. 원본 한 건의 여러 방문·부분 완료·증빙·취소·반품이 어디에 연결되는지 필요한 범위에서 추적한다.
- **한도와 잔여 처리를 끝까지 확인한다.** 예를 들어 가상 주문 240개와 작업당 한도 60개이면 수량만 계산한 최소 작업 수는 4개다. 시간 등의 제약으로 2개 작업만 가능하다면 120개 처리 예정과 잔여 120개를 구분한다. 작업 수를 늘리는 것만으로 원본 수량을 나눌 수 있다고 가정하거나 무한 재시도하지 않는다. 예시 한도는 확정 정책과 구분하고, 일부 처리의 확인 절차와 잔여 처리 주체를 미정 사항에 남긴다.
- **같은 사례를 여러 관점에서 따라간다.** 정상 처리뿐 아니라 한도 직전·초과·0, 빈 입력, 분할 금지, 부분 실패와 재시도 중 관련 사례를 고른다. 입력·행동·예상 수량/상태·실제 결과를 기록한다. HTML에서 중복 요청을 한 번 집계한 결과와 실제 서버의 동시성·재전송 보장을 구분한다.

수량 검증식에는 적용 범위를 적는다. 예를 들어 취소가 없는 시연에서는 `원본 수량 = 완료 + 배정 잔여 + 미배정`으로 확인할 수 있다. 전체 배정량에 완료량이 이미 포함되어 있다면 완료량을 다시 더하지 않는다. 실제 취소·반품 정책은 별도로 확정한다. 이 예시를 모든 제품의 공통 업무 규칙으로 고정하지 않는다.

## 기획과 FE/BE 수정 범위

기획 문서에 아래 정도를 간략히 포함한다. `../assets/product-comparison-plan.md`를 시작점으로 쓸 수 있다.

| 항목 | 적을 내용 |
| --- | --- |
| 문제와 Before/After | 누가 어떤 상황에서 어려움을 겪고, 변경 후 어떤 행동을 할 수 있는지 |
| 기준 자료 | 제품·화면 경로·저장소·읽은 커밋·확인 방법과 한계 |
| 유지·변경·생략 | 기존 배치와 기능 중 무엇을 유지하고 어디를 추가하거나 축약했는지 |
| FE | 실제 페이지·컴포넌트·API 호출·응답 타입·문구 파일과 예상 변경 |
| BE | 실제 컨트롤러·서비스·응답 계약·기존 API 재사용과 필요한 확장 |
| 미정 사항 | 집계 단위·필터/페이지 범위·상태 전환·권한 등 구현 전에 정할 내용 |
| 완료 조건 | 사용자가 확인할 동작, 실패 시 유지할 상태, 이번에 하지 않을 일 |

확인하지 못한 경로나 응답 필드를 만들어 쓰지 않는다. 경로는 저장소 상대 경로로 적고 실제 존재하는지 확인한다. 기존 API에 이미 있는 오류 코드·처리 결과를 먼저 확인한 뒤 새 API 필요성을 판단한다. 확정된 수정 대상과 “기존 응답 확장 또는 별도 API 검토” 같은 후보를 구분한다. 기획에서 코드를 읽은 것과 구현을 마친 것은 다르다.

## 첨부와 공유

- 보드의 `localhost`, `127.0.0.1`, `[::1]` 및 `file://` 링크는 작성자 컴퓨터용이다. 로컬 검토에는 사용할 수 있지만 Jira·Confluence·GitHub 본문이나 공유 첨부 안에 수신자용 링크로 넣지 않는다. 임시 폴더나 절대 로컬 경로도 공유 경로로 쓰지 않는다.
- 단일 HTML 요청이면 CSS·JavaScript·샘플 데이터를 포함한 파일 하나를 첨부한다. 외부 폰트·CDN·네트워크 요청·로컬 저장소·별도 파일·iframe에 의존하지 않게 한다. 로컬 주소를 임의의 공개 URL로 바꾸거나 승인 없이 호스팅하지 않는다.
- 이슈 본문에는 Before/After와 FE/BE 범위를 요약하고, “첨부한 파일명” 또는 실제 확인한 첨부 링크를 안내한다. 브라우저 미리보기가 없으면 다운로드해 여는 방법을 적는다.
- 이슈 구조와 상태 변경은 사용자 요청을 따른다. 특정 사례의 에픽–스토리–하위 작업 구성을 모든 기획에 강제하지 않는다. 관련 없는 티켓 번호를 관성적으로 연결하거나 기획 산출물만으로 개발 이슈를 완료 처리하지 않는다.
- 생성 전에 대상 프로젝트의 이슈 유형·필수 필드·부모 지정 여부를 확인한다. 필수 기한 등 사용자가 정하지 않은 업무 값을 임의로 채우지 말고, 본문과 첨부를 준비한 뒤 필요한 값만 확인한다. 생성 응답의 이슈 식별자를 보관하고, 응답이 불명확하면 실제 생성 여부를 조회한 뒤 재시도한다.
- 첨부 후 실제 이슈를 다시 읽어 파일명·개수·내용과 남은 로컬 링크를 확인한다. 기존 결과물을 자동 삭제하지 않으며, 단일 파일 교체가 필요하면 허용된 범위를 확인한다. 저장된 본문에서 비어 있는 “보드 리뷰:” 같은 안내도 제거한다.
- 여러 관점의 비교본이면 **관점별 단일 HTML**을 각각 첨부한다. 최종 전달 목록에 관점·파일명·공통 기획 버전·파일 크기·SHA-256을 기록해 제작 중간 파일과 구분한다. 보드와 이슈의 해당 결과물을 다시 내려받아 원본 바이트 또는 해시를 비교한다. 다운로드를 확인하지 못했다면 파일명·크기만 확인한 것으로 보고한다. 새 이슈의 유형·기한·부모 관계도 실제 저장값으로 확인한다.
- 회사 사례를 일반 템플릿이나 개인 저장소로 옮길 때 실제 코드·고객명·운영 데이터·비공개 링크를 복사하지 않는다. 재사용할 제작 방식만 가상의 내용으로 정리한다.

## 확인하고 보고

파일을 직접 열어 모드 전환·강조·초기화·주요 상태 전환을 눌러본다. 보드에서도 확인했다면 sandbox 안의 확인 범위를 별도로 적는다. 어느 한쪽만 확인했는데 둘 다 검증했다고 보고하지 않는다. 비교 모드를 바꿔도 입력이 유지되는지, 좁은 폭에서 표와 버튼을 읽고 조작할 수 있는지 확인한다.

최종 보고에는 비교본, 짧은 Before/After 설명, FE/BE 범위, 남은 결정과 실제 확인 범위를 담는다. 보드 저장, 외부 첨부, 스킬 설치, 제품 구현 완료를 서로 구분한다.
