# 공통 기획과 표현별 결과물

같은 기능을 제품 화면·독립 앱·발표 자료로 표현하는 요청에 적용한다. 클린 아키텍처의 의존 방향을 기획에 참고하되, 모든 기획에 실행 코어나 프레임워크를 만들라는 뜻은 아니다.

## 공통 기준

공통 기획에는 해결할 문제, 주체, 핵심 개념, 판단 규칙, 상태 전환, 항상 지킬 조건, 미정 사항을 둔다. UI 경로·색·컴포넌트·슬라이드 좌표는 넣지 않는다. 간단하면 Markdown으로 충분하고 여러 표현에서 값과 사례를 재사용할 때 JSON과 순수 분류 함수를 고려한다. 사실·확인하지 못한 가정·제안을 구분한다.

제품 표현은 공통 개념을 해당 제품의 말과 화면으로 연결한다. 발표 표현은 청중이 알아야 할 흐름을 압축한다. 같은 기능의 표현 차이는 별개 기능안이 아니므로 “제품 적용”, “독립 시연”, “발표용 흐름”처럼 목적을 붙인다. 서로 다른 기능 가설이나 승인 조건이면 공통 기획의 변형으로 명시한다.

## 기존 제품에 맞추는 요청

1. 저장소와 요청한 기준 브랜치를 확인하고 실제 읽은 커밋을 기록한다. 최신 조회가 실패하면 로컬 기준이라는 한계를 밝힌다.
2. 페이지 진입 경로·탭·표·상세 창·문구·디자인 토큰·공통 컴포넌트를 읽는다. 기존 화면이 실행 가능하면 함께 비교하되 운영 데이터를 불필요하게 복사하지 않는다.
3. 무엇을 유지하고 무엇을 추가·축약하는지 적는다. HTML로 외관만 재구성했다면 실제 제품 컴포넌트를 실행했다고 말하지 않는다.
4. 기존 행동과 공통 기획이 충돌하는 부분을 명시한다. 동일한 ‘승인’ 버튼이라도 저장 결과가 다르면 출처별 확인 문구와 처리 경로를 구분한다.

## 표현 연결 명세

실제 보드 API에 없는 필드를 요청에 임의로 추가하지 않는다. 현재 plan/html/source만 지원하면 `source` JSON으로 다음 정도의 연결 명세를 저장한다. 필수 범위를 늘리기보다 이번 결과물이 다시 만들어질 때 필요한 정보를 남긴다.

```json
{
  "schemaVersion": 1,
  "core": { "id": "feature-id", "version": "1.0.0", "file": "core.json", "sha256": "실제 파일에서 계산" },
  "adapters": [
    {
      "id": "product-view", "purpose": "제품 화면 적용", "file": "product.html",
      "baseline": { "repository": "확인한 저장소", "commit": "읽은 커밋", "route": "확인한 화면 경로" },
      "invariants": ["C01"],
      "presentationChanges": ["기존 표에 판단 근거를 표시"],
      "behaviorDifferences": ["기존 동작과 달라지는 부분"],
      "omitted": ["표현에서 생략한 항목"]
    }
  ]
}
```

자동 생성하는 경우 각 HTML 안에 공통 버전·해시를 남기고 공통 파일을 읽어 포함한다. 파일 하나로 실행하는 결과물은 빌드 시 복사본이며 원본 수정에 자동 반응하지 않는다. React·HTML·PPTX가 같은 함수를 실행할 필요는 없지만 같은 조건을 다르게 설명해서는 안 된다. 발표 파일에도 노트나 작은 출처 표기로 공통 버전을 남긴다.

해시 대상인 공통 파일은 제작 전에 확정하고, 자기 해시·생성한 HTML의 해시·등록 식별자·실제 검증 결과를 뒤에 덧붙이지 않는다. Markdown 한 파일을 공통 기획으로 사용해도 같다. 제작 후 내용은 [별도 확인 보고](../assets/product-comparison-report.md)나 `final-artifacts.json`에서 확정 원본의 파일명·버전·해시를 참조한다. 보고서 자체의 해시나 등록 결과를 그 보고서 안에 다시 넣지 않는다. 원본 내용을 바꿔야 한다면 새 버전으로 처리한다.

## 변경과 검토

- 색·배치·표의 열만 바뀌면 해당 표현물의 새 버전과 연결 명세를 만든다.
- 판단 기준·승인 효과·상태 전환이 바뀌면 공통 버전을 올리고 연결된 모든 표현물을 영향 검토한다. 재생성하지 않은 것은 이전 버전으로 표시한다.
- 상태 전환의 예시를 하나 이상 끝까지 확인한다. 제품 화면과 발표 자료에서 자동 승인 여부·등록 효과·실패 분기가 서로 모순되지 않는지 본다.
- 표현별 완료 조건을 적는다. HTML은 주요 동작·빈 상태·독립 실행, 발표 파일은 내용·읽기 쉬운 배치·편집 가능성 등 목적에 맞게 확인한다.
- 보드의 단일 시안 채택 UI와 공통 기획의 채택은 현재 별개 개념이다. 요청 없이 표현물을 자동 채택하지 않는다. 공통 기획 채택·표현별 확인·오래된 표현 표시 기능은 구현되지 않았다면 후속 제안으로 분리한다.
- 여러 관점의 Before/After라면 관점과 설계 선택지를 구분하고, [여러 화면과 데이터 흐름 비교](product-comparison.md#여러-화면과-데이터-흐름-비교)에 따라 같은 원본 사례가 입력·실행·집계까지 어떻게 이어지는지 확인한다. 표면의 숫자가 같다는 이유만으로 처리 단위도 같다고 판단하지 않는다.
- 반복 제작한 결과물은 최종 전달 목록으로 묶는다. 관점·파일명·공통 버전·결과물 파일 해시와 실제 반환된 artifact/proposal 식별자를 연결한다. 공통 파일 해시와 각 HTML 파일 해시는 서로 다른 값이다. 먼저 공통 파일의 확정된 바이트를 해시하고 HTML을 생성한 뒤, 각 완성 파일의 해시를 별도로 계산한다. 아직 반환받지 않은 보드 식별자를 만들어 넣지 않는다.
- 최종 전달 목록은 `source` 결과물로 추가할 수 있다. 결과물을 다시 만들 때는 새 파일과 새 목록을 추가하고, 바꾸지 않은 관점의 버전도 명시한다. 이는 작업자가 관리하는 목록이며 보드가 자동으로 최신 버전·연결 일치 여부를 확인하는 기능은 아니다. 외부 공유 시 로컬 보드 URL 대신 첨부 파일명이나 확인한 공유 링크를 안내한다.

## PPTX와 독립 앱

현재 보드가 바이너리를 지원하지 않으면 발표 HTML을 검토용으로 저장하고 PPTX는 별도 파일로 전달한다. PPTX를 Base64 텍스트로 우회 저장하거나 보드에서 다운로드 가능하다고 단정하지 않는다. 실제 보드 저장 기능 확장은 별도 구현 범위다.

독립 HTML은 외부 의존성 없이 열리게 한다. React로 옮길 가능성은 공통 상태·기능과 제품별 화면/저장소 연결의 경계로 설명한다. 실제 분석·인증·영구 저장·예약 실행이 필요하면 브라우저 화면을 호스팅하는 일과 서버 기능을 분리해서 적는다. 단순 시안 요청을 실제 서비스 배포로 확대하지 않는다.
