# 화면과 저장, 기획 작업을 연결하는 방식

현재 초안은 **로컬 서버 한 개 + 파일 저장 + 보드 화면 + 스킬용 CLI**로 동작합니다. Docker·DB·외부 API 없이 사용할 수 있습니다.

## 각 부분의 책임

| 위치 | 맡는 일 |
| --- | --- |
| src/core/model.ts, board.ts | 공통 데이터, 연결 검사, 목록과 준비 상태 계산 |
| src/core/repository.ts | 화면의 조회·채택·준비 확인 명령을 API로 전달. 브라우저 예제 저장도 별도 제공 |
| src/components/ | 프로젝트 선택, 공통 카드, 시안 비교, 진행 기록 표시 |
| server/http.mjs | 같은 주소에서 화면·API·격리한 HTML 제공 |
| server/service.mjs | 접수, 상태 변경, 결과물 연결, 요청 중복 방지, 검토 충돌 검사 |
| server/store.mjs | 저장 폴더 잠금, 쓰기 순서 보장, JSON 교체 저장, 파일 보관 |
| .agents/skills/prototype-board/ | 기획 수행 절차와 설치 위치에 의존하지 않는 CLI |
| src/examples/ | 브라우저 예제. 실제 작업 기록과 분리 |

CLI와 화면은 같은 HTTP API를 사용합니다. 화면용 전체 스냅샷 덮어쓰기는 제공하지 않습니다. 이후 DB를 붙일 때는 먼저 FileStore의 read/transaction/writeArtifact/readArtifact 동작을 대체하면 됩니다. 현재 transaction은 전체 스냅샷을 메모리에서 수정하므로 대용량 DB에 그대로 최적화되어 있다는 뜻은 아닙니다.

## 저장 관계

- 프로젝트 안에 기획 주제(Idea)가 있습니다.
- 접수 시 주제와 작업(Run)을 만들고, 요청 범위·수행 주체·확인된 원래 작업 정보를 남깁니다.
- 기획 문서·HTML·소스 파일(Artifact)은 주제와 작업에 연결됩니다.
- HTML 하나를 저장하면 비교할 시안(Proposal) 하나가 생깁니다. 파일은 덮어쓰지 않습니다.
- 준비 항목은 시안에 속하고, 주제의 selectedProposalId가 현재 채택안을 가리킵니다.
- 시안이 없으면 준비 중, 시안이 있거나 문서 검토 요청을 마쳤으면 검토 중입니다. 채택하면 통과, 채택안의 준비 항목을 모두 확인하면 개발 준비입니다.

통과 목록은 같은 주제와 채택안을 조회합니다. 별도 카드 복사본이 없습니다. 문서만 만든 기획은 검토할 시안 목록에서 문서를 볼 수 있지만, 문서 자체를 채택하는 기능은 아직 없습니다.

## 기획 진행과 사용자 검토를 구분

작업 상태는 접수 → 기획 → 화면 제작 → 검토 요청입니다. 문서만 요청하면 화면 제작을 생략합니다. 진행 중 확인이 필요하면 blocked, 중단하면 cancelled로 기록합니다.

검토 요청은 ‘필요한 결과물이 저장되어 사용자가 볼 수 있음’을 뜻합니다. 사용자 승인이나 실제 제품 개발 완료가 아닙니다. 화면의 채택·개발 준비 확인은 별도로 남깁니다.

기록은 수행 중인 에이전트가 남긴 보고입니다. 다른 모델이 실제 실행됐다는 독립적인 증명, 사용량·비용 측정, 자동 작업 배분은 제공하지 않습니다.

## 저장과 충돌 처리

저장 폴더에는 board.json, artifacts/, .writer.lock이 있습니다. 기본 경로는 ~/.local/share/prototype-board/workspaces/personal이며 --data-dir로 바꿀 수 있습니다.

서버 하나가 폴더를 소유하고 요청을 순서대로 반영합니다. 매번 임시 JSON을 쓰고 기존 JSON과 교체합니다. 실패한 변경은 메모리의 마지막 성공 데이터에도 반영하지 않습니다. 다수의 CLI·탭이 한 서버로 접수할 수 있습니다.

각 쓰기는 requestId를 사용합니다. 같은 내용·같은 ID는 이전 결과를 돌려주고, 같은 ID에 다른 내용이 오면 409로 거절합니다. 화면의 검토 명령은 읽었던 revision도 확인하므로 다른 작업의 결과를 오래된 화면이 덮어쓰지 않습니다. 화면은 활성 상태에서 약 2초마다 최신 내용을 읽습니다.

파일을 먼저 보관한 뒤 JSON에 연결합니다. 저장이 중단되면 연결되지 않은 파일이 남을 수 있지만 API로 노출하지 않습니다. 현재 초안에는 자동 파일 정리·버전 마이그레이션·백업 복구 UI가 없습니다. 전체 데이터가 메모리에 올라가므로 대규모 저장, 여러 서버, 전원 장애까지 포함한 DB 수준 내구성은 보장하지 않습니다.

## 실행과 자료의 경계

- 서버 바인딩 주소와 포트는 `PROTOTYPE_BOARD_HOST`, `PROTOTYPE_BOARD_PORT`로 정합니다. 동일 주소에서 화면과 API를 제공하므로 별도 CORS 설정이 필요하지 않습니다.
- Host·Origin·보드 식별자·쓰기 헤더를 검사하고 허용하지 않은 웹사이트에서 시작한 요청을 거절합니다. 같은 컴퓨터의 다른 프로그램을 막는 로그인·권한 기능은 아닙니다.
- 저장소 연결 설정이 없을 때 개인 보드를 임의로 고르지 않습니다. 프로필의 workspaceId로 포트가 다른 보드에 재사용되는 경우도 검사합니다.
- 개인 자료와 조직 자료는 **서로 다른 데이터 폴더·서버·연결 설정**을 사용합니다. 프로젝트 필터나 private fork만으로 자료 접근이 분리되지는 않습니다.
- HTML은 sandbox="allow-scripts"와 응답 CSP를 함께 적용합니다. allow-same-origin은 허용하지 않으며 외부 통신·보드 API·팝업·폼 제출을 막습니다. 이 제한은 악성 코드의 CPU 점유 등 모든 위험을 격리하는 보안 실행 환경을 뜻하지 않습니다.
- React·TSX·기타 소스는 파일로 보관할 뿐 서버에서 실행하지 않습니다. 직접 시도할 화면은 독립 HTML로 저장합니다.

## 후속 작업

1. 기획 수정·보관·삭제와 감사 이력, 같은 주제 안에서 재작업 시작하기
2. 파일 백업·내보내기·복구·미연결 파일 정리
3. 문서 자체를 검토하고 채택하기, 기획 질문의 결정 이력
4. 실제 작업 전달과 회신, 실패 재시도·실행 제한·비용 측정
5. 다중 사용자 인증, DB 구현, 대용량 목록 조회

자동화 범위는 저장 기반을 먼저 확인한 뒤 확장합니다. 카드 JSX를 직접 수정해서 기획을 등록하거나, 예정된 모델 호출을 이미 실행한 것처럼 표시하지 않습니다.
